### 实现期的补充决定

1. **询问时机是「发起」而不是「创建」（业务纠正）**
   最初按本文档 §7.1 的原稿放在了新建/编辑弹窗。业务确认后改为：**只在列表操作栏点「发起审批流程」时询问**，创建/编辑弹窗不再询问，避免同一件事被问两遍。详见 §7.1。
   为此新增了专用接口 `POST /monthly-measurements/:id/safety-measure-merge`：只更新并入配置与清单项标记，**不重建明细**，避免冲掉已录入的各方数量。

2. **明细页用行内 Badge 而不是新增表格列**
   该表格是 25 列三层表头，新增列需要同步改表头 colspan 与每一行的单元格，风险高于收益。改为在清单名称旁显示只读「安措费」标签（与既有「验收:N」标签同一模式），并在表格上方显示"本期已并入，共 N 项清单"的汇总提示。

### 联调发现并修复的问题

**问题 1：手工新建拦截过严（§6.5）**

原实现用手工新建接口的拦截条件是"**同期已存在由月度验工生成的隐藏记录**"。联调中发现：隐藏记录在月度验工被驳回/撤销后会保留为 `CANCELED`（这是有意的，便于审计），但该记录**会永久阻断同期的手工新建**——即使用户已经关闭了并入开关。

已改为判断"**同期是否仍存在 `includeSafetyMeasure = true` 的月度验工**"，这才是"本期已并入"的真正信号；关闭开关后即可正常手工新建。错误提示也改为可操作的引导文案。

**问题 2：并入配置接口的"可编辑"判断误用 binding 状态**

新接口最初用 `approval_flow_bindings.status` 判断可否修改。联调中发现：流程被「重置未送审」后，单据已可编辑，但 binding 会残留 `CANCELED`，导致**重置后无法再配置并入**。

已改为判断单据自身的 `monthly_measurements.approveStatus`（草稿/START/RETURNED 才允许），与 `checkEditableBeforeFlowEnd` 的口径一致。

**问题 3（最隐蔽）：baseDate 存储口径不一致，导致同月单据看不到 0 期数据**

线上走完 0 期月度验工流程后，**同月**新建的安全文明措施费累计完成数仍然是 0。

排查结果：写回本身是成功的（隐藏记录已生成、金额正确），问题出在**时间戳口径**：

| 对象               | baseDate 存法                            | 2026-09 的实际值            |
| ------------------ | ---------------------------------------- | --------------------------- |
| 月度验工           | `dayjs(...).endOf('month').endOf('day')` | 2026-09-30 **23:59:59.999** |
| 手工安全文明措施费 | 月初                                     | 2026-09-01 **00:00:00.000** |
| 隐藏记录（修复前） | 直接复制月度验工                         | 2026-09-30 **23:59:59.999** |

累计规则是「`baseDate` 更早，或相等时 `code` 更小」。同月时隐藏记录恒**大于**手工单据，于是被判为"更晚"而排除——**只有更晚月份的单据才看得到它**。

> 这也是为什么早期的验证没暴露它：我当时用下一个月的单据测试，恰好绕过了同月场景。

**已修复**：新增 `normalizeSafetyMeasureBaseDate()`，把隐藏记录的 `baseDate` 归一化到**当月月初**，与手工单据口径对齐；同月时改走 `code` 比较，而自动生成的 `000` 序号恒小于手工单据。已加单元测试锁定该不变量（归一化后不晚于原值、不改变所属月份、幂等）。

## 1. 背景与需求

### 1.1 业务流程现状

| 场景                    | 现状做法                                                                                                                           |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **标准流程**（非 0 期） | 先建【安全文明措施费】并走完它**自己的**审批流 → 再在【月度验工】里**关联**该措施费 → 关联动作把措施费的各方数量带入月度验工清单项 |
| **0 期特例**            | 0 期没有可关联的措施费单据，用户在【月度验工】明细页**手写**安全文明措施费数据                                                     |

### 1.2 本次需求

针对 **0 期**【月度验工】：

1. **不需要关联**【安全文明措施费】；
2. 手写的安全文明措施费数据，在**月度验工流程审批通过后**，必须统计进【安全文明措施费】的**累计完成数**；
3. 后续新发起的【安全文明措施费】，其累计完成数要包含这笔 0 期数据。

### 1.3 过渡性（重要）

0 期特例是**过渡方案**。后续业务会统一切换到标准流程（先走完安全文明措施费，再关联到月度验工）。

因此本方案用一个**显式开关** `includeSafetyMeasure` 区分，**不把"0 期"逻辑写死在代码里**；切换时只需关闭开关，标准流程代码路径完全不受影响。

## 3. 现状关键机制（方案的地基）

均来自当前代码，方案设计必须与之一致：

1. **安全文明措施费的清单范围 = 新建时选择的"分部工程"**
   新建单据时选 `boqSectionIds`，后端取这些分部工程下的全部 BOQ 节点（含逐级祖先，祖先到 `CATEGORY` 为止），落成 `safety_measure_items`。
   依据：`packages/server/modules/quality-acceptance-form/rest/router.ts`（新建安全文明措施费，约 3937 行起）。

2. **安全文明措施费的"累计完成数"只认自己家已审批通过的单据**
   `GET /safety-measures/:id/items` 统计其他 `approveStatus='APPROVED'` 且 `baseDate`（同月时比较 `code`）早于本单的 `safety_measure_items`；取值优先级为
   `contractDeptQty > engineeringQty > headquartersQty > supervisionQty > contractorQty`。
   列表页的"累计金额"同理（`rest/router.ts` 约 3419 行）。

   👉 **这是本方案最关键的一点**：只要写回的 0 期数据在库里是一条 `approveStatus='APPROVED'` 的 `safety_measures` 记录，后续单据的累计统计**零改动**即可纳入。

   > ⚠️ **易错点：当前代码里，安全文明措施费的累计与月度验工毫无关系。**
   > 累计只要求"**安全文明措施费自己**的其他单据已审批通过"，**不要求**关联到月度验工，**也完全不看**月度验工是否走完流程。
   >
   > 这正是本次需求要补的缺口：**当前不存在"月度验工 → 措施费累计"的链路**，必须新增（§4），而不是靠配置或关联就能自动生效。下面这张表描述的是**改代码之前**的行为。
   > `safetyMeasureId`（`monthly_measurements` 上的字段）方向是**反的**：它只负责把措施费的量**带入**月度验工，并让该单据从"关联下拉"消失（`unoccupied` 子查询）。
   > 注意区分同名字段：`safety_measure_items.safetyMeasureId` 是明细指向自己父单据的外键，与月度验工无关（见 `rest/router.ts:3374-3398`）。
   >
   > |                        | 统计来源                                                                          | 要求关联月度验工 | 要求流程走完               |
   > | ---------------------- | --------------------------------------------------------------------------------- | ---------------- | -------------------------- |
   > | **安全文明措施费**累计 | 本项目其他 `safety_measures`（`approveStatus='APPROVED'`）的明细                  | 否               | 要求**措施费自己**已通过   |
   > | **月度验工**累计       | 本项目其他 `monthly_measurements`（`approveStatus='APPROVED'`）的 `investmentQty` | 否               | 要求**月度验工自己**已通过 |
   >
   > 附带发现（既有行为，非本次引入）：一张已审批通过的安全文明措施费，之后若被月度验工关联，会在两本账里各计一次。这正是 §9.1「重复计量」校验必须做的原因。

3. **月度验工已有反向关联链路**
   `monthly_measurements.safetyMeasureId` 已存在；关联时用安全文明措施费的 `contractorQty/supervisionQty/headquartersQty/engineeringQty` 覆盖月度验工的 `contractorQty/supervisionQty/headquartersQty/investmentQty`。
   依据：`services/monthlyMeasurements.ts:529-550`、`rest/router.ts`（`associate-safety-measure`，约 1604 行）。
   👉 已有的口径映射就是 **engineering(工管) ↔ investment(投资监理)**，与决策 2 一致。

4. **月度验工明细 = 项目全量 BOQ 树**
   `buildPreview` 取 `getProjectBoqItems(projectId)` 全量，`isSummaryRow = 该节点有子节点`。
   👉 写回数据可以**完全从 `monthly_measurement_items` 派生**，不需要回查 BOQ 树，且节点集合与安全文明措施费的口径天然对齐。

5. **流程回写 hook 只能改"本单据"的字段**
   `flow/services/approvalFlows.ts` 的 hook 体系只支持 `updateResourceFields`（同资源），**跨单据写回必须写代码**。

6. **月度验工没有"工程管理部"角色/字段**
   明细录入列只有：施工单位 / 施工监理 / 现场指挥部 / 投资监理（`acceptance-edit.vue:124-129`）。
   权限角色：`contractor / supervision / headquarters / investment / contract / leader / owner`（`rest/router.ts:721-800`）。

7. **状态保护**
   月度验工送审后不可编辑（`rest/router.ts:1240-1243`）；已审批通过不可删除（`rest/router.ts:1565-1574`）。

## 4. 方案总览

```text
发起 0 期月度验工
      │
      ├─ 弹窗：是否包含本期安全文明措施费？
      │        │
      │        ├─ 否 → 正常发起月度验工（现状不变）
      │        │
      │        └─ 是 → 选择"分部工程"（复用安全文明措施费的选法）
      │                 │
      │                 ▼
      │         后端按分部工程在 monthly_measurement_items 上打标
      │         isSafetyMeasure = true（叶子命中 + 祖先补全）
      │
      ▼
月度验工审批流（各方在明细页录 施工/监理/指挥部/投资监理 数量）
      │
      ├─ 审批通过 ──► 幂等 upsert 一条【隐藏】的 safety_measures + safety_measure_items
      │               · approveStatus = 'APPROVED'
      │               · sourceMeasurementId = 月度验工 id
      │               · engineeringQty = 月度验工 investmentQty
      │                              │
      │                              ▼
      │               后续手工安全文明措施费的"累计完成数"自动包含它
      │               （累计查询无需改动）
      │
      ├─ 驳回 / 取消 ──► 隐藏记录置为 CANCELED（累计查询自动排除）
      │
      └─ 再次送审通过 ──► 幂等 upsert 覆盖
```

## 6. 后端改动清单

### 6.1 清单项打标（`services/monthlyMeasurements.ts`）

1. `MonthlyMeasurementPreviewItem` 增加 `isSafetyMeasure: boolean`。
2. `buildPreview` 入参增加 `safetySectionIds?: string[]`；在 `includedItems` 循环（约 262-301 行）前先算出命中集合，然后逐行赋值。

   算法**必须与新建安全文明措施费完全一致**（`rest/router.ts` 新建逻辑），否则两侧 `boqItemId` 集合会对不齐，累计数就对不上：

   ```text
   selectedSections = Set(safetySectionIds)
   itemMap          = Map(boqItems by id)

   // 第一步：命中 = 选中的分部工程本身 + 其全部后代
   hit = Set(boqItems.filter(isDescendantOfSelectedSection).map(id))

   // 第二步：补祖先，到 CATEGORY 为止（含 CATEGORY）
   for id of hit:
     cur = itemMap.get(id)
     while cur?.parentId:
       parent = itemMap.get(cur.parentId)
       if parent:
         hit.add(parent.id)
         if parent.type === 'CATEGORY': break
       cur = parent

   isSafetyMeasure = hit.has(item.id)
   ```

3. `createMonthlyMeasurementFromPreviewFactory` 入参增加 `safetySectionIds`，透传给 `buildPreview`，并在生成 `items` 时写入 `isSafetyMeasure`。

| `investmentQty × price`                                              | **`engineeringAmount`**                                                                                                                 |                                        |
| —                                                                    | `contractorQty/contractorAmount/supervisionQty/supervisionAmount/headquartersQty/headquartersAmount/contractDeptQty/contractDeptAmount` | **全部保持 0**                         |

> ⚠️ 为什么其余角色列必须为 0：累计取值是"按优先级取第一个非 0 值"（`contractDeptQty || engineeringQty || headquartersQty || ...`）。若把施工/监理/指挥部的量也写进去，当投资监理量为 0 时，累计会**串位**取到指挥部或施工的量。全部置 0 后，该单据的累计值严格等于"投资监理量"。

同时插入一条空的 `safety_measure_details`（避免详情接口走到自动补建的兜底分支）。

## 8. 状态机 / 幂等 / 撤销

| 月度验工状态           | 隐藏安全文明措施费记录           | 后续单据累计是否包含 |
| ---------------------- | -------------------------------- | -------------------- |
| 草稿 / 审批中          | 尚不存在                         | 否                   |
| 已通过 APPROVED        | 存在，`approveStatus='APPROVED'` | **是**               |
| 已通过 → 撤销 CANCELED | `approveStatus='CANCELED'`       | 否（自动回退）       |
| 驳回 REJECTED          | `approveStatus='CANCELED'`       | 否                   |
| 驳回后再次送审通过     | upsert 覆盖，恢复 `APPROVED`     | 是                   |

**幂等保证**：唯一索引 `safety_measures.sourceMeasurementId` + "先删 items 再重建"的 upsert。
**撤销保证**：非 APPROVED 终态一律置 CANCELED，累计查询天然排除，无需额外清理。
**删除**：已审批通过的月度验工不可删除（现有约束），因此不需要额外的级联删除逻辑。

## 9. 关键校验与边界

1. **重复计量**：同期只允许一种来源。`includeSafetyMeasure = true` 与手工新建安全文明措施费互相排斥（6.2 / 6.5）。
2. **同项目多张并入单**：需要校验同一 `baseDate`（或 `roundName = '0'`）下最多一张 `includeSafetyMeasure = true` 的月度验工，否则会重复累计。建议在 6.2 的校验里一并加上。
3. **序号保留**：`AQWM-YYYYMM-000` 保留给自动生成。手工创建的取号逻辑是 `max(已有序号) + 1`，遇到 `000`（parseInt = 0）仍会从 `001` 开始，不会冲突。
4. **排序正确性**：月度验工的 `baseDate` 就是 0 期的年月，通常早于后续手工单据；同月时靠 `code` 的 `000` 兜底排在最前。
5. **存量数据**：`includeSafetyMeasure` 默认 false，历史单据完全不受影响。
6. **关联下拉隔离**：隐藏记录不得出现在月度验工的"关联安全文明措施费"下拉中，否则用户一关联就会用它的数量覆盖月度验工。
7. **汇总金额**：`aggregated-items` 是否要把安全文明措施费部分单列，见「待确认」。

## 10. 存量数据回填（一次性，必做）

"当前只有 0 期的月度验工手写安全文明措施费数据"意味着：**很可能已经存在审批通过的 0 期月度验工**，它们的措施费数据同样没有进入措施费累计。

而新代码只在"审批通过事件"上触发写回，**不会追溯历史单据**。因此上线时必须配套一次性回填，否则这些项目的措施费累计会长期缺一块。

回填步骤：

1. 找出所有 `roundName = '0'` 且 `approveStatus = 'APPROVED'` 的月度验工；
2. **逐张补齐 `safetySectionIds`** —— 这是回填唯一的人工输入。历史单据没有分部工程标记，无法自动推导，必须由业务确认"这张 0 期验工里哪些分部工程属于安全文明措施费"；
3. 调用与线上**完全相同**的 `syncSafetyMeasureFromMonthlyMeasurement({ status: 'APPROVED' })` 生成隐藏记录。

注意事项：

- 必须复用线上同一个同步函数，**不要另写一套 SQL**，否则口径必然漂移。
- 回填前需确认这批历史单据的措施费数据确实填在**投资监理**列，否则 §2 决策 2 的前提不成立。脚本会在干跑时自检：若匹配到了清单项但「投资监理」金额合计为 0，会打印告警，提示口径可能不符。
- ~~需先盘点是否存在"同期既有手工安全文明措施费、又有 0 期月度验工并入"的项目~~ → **业务已确认存量不存在同期单据**，无重复计量风险。脚本里的同期拦截保留作为安全网（零成本），并覆盖将来手工补建同期单据的情况。

## 13. 待确认 / 风险

1. **`aggregated-items` 的展示口径**：0 期的安全文明措施费金额是否需要在月度验工汇总页**单列一行**（如"安全文明措施费"章节），还是并入原有清单行即可？当前方案默认**并入**。
